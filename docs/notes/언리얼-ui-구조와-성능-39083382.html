언리얼 UI 구조와 성능

결론부터 말씀드리면, 언리얼엔진 UI에 깊게 파고들었다는 것은 “UMG로 예쁜 화면을 만들 줄 안다”가 아니라, UI가 엔진 내부에서 어떻게 생성되고, 입력을 받고, 포커스를 잡고, 레이아웃되고, 페인트되고, 캐시되고, 성능 병목을 만들며, 프로젝트 구조 안에서 어떻게 확장되어야 하는지 설명하고 고칠 수 있는 상태를 말합니다.

가장 짧게 정의하면 이렇습니다.

UMG를 사용하는 사람은 위젯을 만듭니다.

UI를 깊게 파본 사람은 UMG, Slate, 입력 라우팅, 포커스, 생명주기, 성능, 데이터 바인딩, UI 아키텍처까지 책임 경계를 나눠 설계합니다.

1. UMG만 아는 수준은 “입문~중급”입니다

예를 들면 이런 정도입니다.

CreateWidget<UUserWidget>(PlayerController, WidgetClass);
Widget->AddToViewport();

또는 Widget Blueprint에서 버튼 만들고, 텍스트 바꾸고, ProgressBar에 체력 값을 바인딩하는 수준입니다.

이것도 당연히 중요합니다. 하지만 “깊게 파고들었다”고 말하기에는 부족합니다. 이 단계는 보통 화면을 구성할 수 있다에 가깝습니다.

깊게 들어가면 다음 질문에 답할 수 있어야 합니다.

NativeOnInitialized()
NativePreConstruct()
NativeConstruct()
NativeDestruct()

각 함수가 언제 호출되는지, 어디에서 Delegate를 바인딩해야 하는지, 어디에서 해제해야 하는지, 왜 NativeConstruct()가 여러 번 호출될 수 있는지, 위젯을 Remove했다가 다시 Add했을 때 상태가 어떻게 유지되거나 초기화되는지 설명할 수 있어야 합니다.

2. UMG 아래에 Slate가 있다는 것을 이해해야 합니다

언리얼의 UI를 깊게 봤다는 것은 결국 UMG와 Slate의 관계를 이해했다는 뜻입니다.

Slate는 언리얼의 UI 프레임워크이고, 언리얼 에디터 UI와 인게임 UI에도 사용됩니다. Epic 문서에서도 Slate를 플랫폼 독립적인 UI 프레임워크로 설명하며, 선언형 문법과 컴포지션을 통해 UI를 구성한다고 설명합니다. (Epic Games Developers)

즉, 깊게 파본 사람은 이런 흐름을 압니다.

UUserWidget / UWidget
        ↓
RebuildWidget()
        ↓
SWidget / SCompoundWidget / SLeafWidget
        ↓
Slate Layout / Paint / Input / HitTest

그리고 필요하면 직접 이런 식의 커스텀 Slate 위젯도 만들 수 있어야 합니다.

class SStatGauge : public SCompoundWidget
{
public:
 SLATE_BEGIN_ARGS(SStatGauge) {}
 SLATE_ATTRIBUTE(float, Value)
 SLATE_END_ARGS()
 void Construct(const FArguments& InArgs)
 {
 Value = InArgs._Value;
 ChildSlot
 [
 SNew(SProgressBar)
 .Percent(this, &SStatGauge::GetPercent)
 ];
 }
private:
 TAttribute<float> Value;
 TOptional<float> GetPercent() const
 {
 return FMath::Clamp(Value.Get(), 0.0f, 1.0f);
 }
};

이 정도를 알면 “UMG 위젯을 조립한다”가 아니라 “언리얼 UI 시스템 위에서 필요한 컴포넌트를 직접 만든다”에 가까워집니다.

3. 입력, 포커스, 내비게이션 문제를 설명할 수 있어야 합니다

UI를 깊게 파본 사람은 “버튼이 안 눌려요”를 단순히 IsFocusable 체크로 끝내지 않습니다.

다음 경계를 봅니다.

PlayerController
Input Mode
Enhanced Input
Viewport
CommonUI / Input Router
Slate Application
Hit Test Grid
Focus Path
Widget

예를 들어 이런 문제를 분석할 수 있어야 합니다.

마우스로는 클릭되는데 게임패드로는 선택이 안 됨
ESC가 게임 입력으로 먹고 UI Back으로 안 감
팝업 뒤의 버튼이 같이 눌림
모달이 떠 있는데 캐릭터가 움직임
위젯은 보이는데 클릭이 안 됨

특히 Common UI까지 봤다면 더 깊은 편입니다. Common UI는 복잡한 멀티 레이어 UI와 크로스 플랫폼 UI를 만들기 위한 플러그인이고, 입력 라우팅과 게임패드/플랫폼별 UI 처리를 지원합니다. (Epic Games Developers) Epic 문서에서도 Common UI의 입력 라우팅은 화면상 위에 렌더된 UI 위젯으로 입력을 보내는 구조라고 설명합니다. (Epic Games Developers)

즉, 깊게 파본 사람은 이런 식으로 설계합니다.

UIInputRouter
    - 현재 활성 레이어 판단
    - Back / Confirm / Cancel 처리
    - 게임 입력 차단 여부 판단

UIScreenStack
    - HUD
    - Menu
    - Modal
    - Toast
    - Loading

각 Widget
    - 자기 입력만 처리
    - 전역 흐름을 직접 제어하지 않음

Manager가 모든 버튼 분기를 처리하는 구조가 아니라, 입력 흐름은 라우터가 오케스트레이션하고, 실제 반응은 각 위젯이 책임지는 구조가 좋습니다.

4. UI 성능을 숫자와 구조로 설명할 수 있어야 합니다

깊게 파봤다는 말에서 가장 큰 차이가 나는 부분이 성능입니다.

얕게 보면 이렇게 말합니다.

Tick 줄이면 됩니다.
Binding 쓰지 마세요.
Retainer Box 쓰면 됩니다.

깊게 보면 이렇게 말합니다.

이 위젯은 매 프레임 Layout Invalidation이 발생합니다.
여기는 Child Invalidation이 너무 자주 납니다.
리스트는 ScrollBox가 아니라 ListView로 가상화해야 합니다.
Retainer Box는 렌더 타깃 비용이 있으므로 먼저 Invalidation Box를 검토해야 합니다.

Epic 문서에 따르면 Invalidation Box는 자식 위젯의 지오메트리를 캐시하고 변경이 없으면 다시 페인트하지 않아 CPU 사용량을 줄입니다. 또한 Slate의 UI 처리에는 Hierarchy, Layout, Paint 단계가 있고, 어떤 변경이 발생했는지에 따라 재계산 비용이 달라집니다. (Epic Games Developers)

Retainer Box는 자식 위젯을 먼저 렌더 타깃에 그린 뒤 그 결과를 화면에 렌더링하며, 렌더 빈도와 phase를 제어할 수 있습니다. (Epic Games Developers) 다만 Epic 문서는 Retainer Panel이 다시 그릴 때 오버헤드와 메모리 비용이 있으므로 CPU 사용량을 줄일 때는 Invalidation Box를 먼저 검토하라고 설명합니다. (Epic Games Developers)

그래서 깊게 파본 사람은 UI 최적화를 이렇게 접근합니다.

1. Tick / Binding 제거
2. 이벤트 기반 갱신으로 변경
3. Widget Tree 재구성 빈도 줄이기
4. Invalidation Box 적용
5. ListView / TileView로 대량 아이템 가상화
6. Retainer Box는 필요한 영역에만 제한적으로 사용
7. Widget Reflector / Insights로 확인

5. Widget Reflector로 실제 UI 트리를 추적할 수 있어야 합니다

“깊게 파봤다”는 말은 디버깅 도구를 쓸 줄 안다는 뜻이기도 합니다.

Widget Reflector는 Slate 위젯을 식별하고 디버깅하기 위한 도구입니다. Epic 문서에 따르면 Widget Reflector는 위젯 계층, 포커스, 클리핑, 소스 정보, Hit Test Grid, 위젯 이벤트 등을 확인할 수 있습니다. (Epic Games Developers)

깊게 파본 사람은 문제가 생겼을 때 이렇게 봅니다.

보이는가?
    Visibility / Render Opacity / Clipping 확인

클릭 가능한가?
    Hit Test Invisible / Self Hit Test Invisible 확인

입력이 들어오는가?
    Hit Test Grid / Focus Path 확인

레이아웃이 맞는가?
    Desired Size / Allotted Geometry 확인

성능 문제가 있는가?
    Invalidation / Paint / Update Debugging 확인

즉, 감으로 고치는 사람이 아니라 UI 트리를 보고 원인을 좁혀가는 사람입니다.

6. 데이터와 화면을 분리할 수 있어야 합니다

깊게 파본 UI 구조는 보통 이런 식이 아닙니다.

void UInventoryWidget::NativeTick(const FGeometry& MyGeometry, float InDeltaTime)
{
 Super::NativeTick(MyGeometry, InDeltaTime);
 HealthText->SetText(FText::AsNumber(Character->GetHealth()));
 AmmoText->SetText(FText::AsNumber(Character->GetAmmo()));
 GoldText->SetText(FText::AsNumber(Character->GetGold()));
}

이 구조는 화면이 게임 도메인을 직접 알고, 매 프레임 데이터를 끌어오고, 테스트도 어렵고, 나중에 UI가 커질수록 망가지기 쉽습니다.

더 나은 구조는 이렇습니다.

CombatComponent
    ↓ 이벤트 발행
CombatViewModel
    ↓ UI에 필요한 표현 상태 보관
CombatHudWidget
    ↓ 표시만 담당
TextBlock / ProgressBar

예시로는 이런 방향입니다.

UCLASS()
class UCombatHudViewModel : public UObject
{
 GENERATED_BODY()
public:
 DECLARE_MULTICAST_DELEGATE_OneParam(FHealthChanged, float);
 FHealthChanged OnHealthChanged;
 void SetHealthRatio(float InRatio)
 {
 const float NewRatio = FMath::Clamp(InRatio, 0.0f, 1.0f);
 if (FMath::IsNearlyEqual(HealthRatio, NewRatio))
 {
 return;
 }
 HealthRatio = NewRatio;
 OnHealthChanged.Broadcast(HealthRatio);
 }
 float GetHealthRatio() const
 {
 return HealthRatio;
 }
private:
 float HealthRatio = 1.0f;
};

void UCombatHudWidget::BindViewModel(UCombatHudViewModel* InViewModel)
{
 if (!InViewModel)
 {
 return;
 }
 ViewModel = InViewModel;
 ViewModel->OnHealthChanged.AddUObject(this, &ThisClass::SetHealthRatio);
 SetHealthRatio(ViewModel->GetHealthRatio());
}
void UCombatHudWidget::SetHealthRatio(float InRatio)
{
 if (!HealthBar)
 {
 return;
 }
 HealthBar->SetPercent(InRatio);
}

언리얼의 MVVM 플러그인도 이런 방향과 맞습니다. Epic 문서는 UI 개발에서 백엔드 데이터와 시각 디자인을 분리하는 흐름을 설명하고, ViewModel이 UI에 사용할 변수를 제공하며 바인딩된 위젯에 업데이트를 푸시한다고 설명합니다. (Epic Games Developers)

핵심은 Widget이 게임 시스템을 직접 뒤지는 구조를 피하고, UI에 필요한 상태를 ViewModel/Presenter가 제공하는 구조입니다.

7. “깊게 파봤다”고 말할 수 있는 실전 기준

아래 항목 중 절반 이상을 직접 구현하거나 디버깅해봤다면 꽤 깊게 본 편입니다.

영역 깊게 봤다는 증거
UMG 생명주기 NativeOnInitialized, NativeConstruct, NativeDestruct, Add/Remove 흐름을 설명 가능
Slate SWidget, SCompoundWidget, RebuildWidget() 기반 커스텀 위젯 구현 가능
입력 마우스, 키보드, 게임패드, Back, Confirm, Focus 문제 해결 가능
Common UI Activatable Widget, Layer, Input Routing, Action 처리 구조 이해
성능 Invalidation, Retainer, Widget Tick, Binding, ListView 가상화 설명 가능
디버깅 Widget Reflector로 Hit Test, Focus, Slate Tree 추적 가능
구조 Widget, ViewModel, UI Router, Screen Stack, Popup Layer 책임 분리 가능
플랫폼 DPI Scaling, Safe Zone, 패드 내비게이션, 로컬라이징 대응 가능
대량 UI 인벤토리, 스킬 트리, 로그, 랭킹, 상점 같은 대량 리스트 최적화 가능
확장성 새 UI 화면 추가 시 기존 Manager 수정이 적은 구조 설계 가능

8. 면접이나 포트폴리오에서 이렇게 말하면 좋습니다

그냥 이렇게 말하면 약합니다.

언리얼 UI를 깊게 파봤습니다.
UMG 많이 써봤고 HUD, 인벤토리, 메뉴 만들었습니다.

더 강하게 말하려면 이렇게 말하는 편이 좋습니다.

UMG 위젯 제작뿐 아니라 Slate 기반 동작 구조까지 확인하면서 UI를 설계했습니다.
Widget 생명주기, Focus/Input Routing, Invalidation, Retainer Box, ListView 가상화 문제를 다뤘고,
HUD/Menu/Modal을 Screen Stack 구조로 분리했습니다.
Widget은 표현만 담당하게 하고, 상태는 ViewModel에서 이벤트 기반으로 전달하도록 구성했습니다.

전투 시뮬레이션 게임 기준으로는 더 구체적으로 이렇게 말할 수 있습니다.

전투 HUD는 전투 도메인과 직접 결합하지 않고 CombatHudViewModel을 통해 체력, 탄약, 상태이상, 타겟 정보를 전달했습니다.
UI는 매 프레임 폴링하지 않고 전투 상태 변경 이벤트를 받아 갱신하도록 만들었으며,
대량 로그와 유닛 리스트는 ListView 기반으로 구성해 위젯 생성 비용을 줄였습니다.
게임패드와 키보드 입력은 UI Layer와 Input Router에서 처리하고,
개별 위젯은 자신의 선택/취소/확정 동작만 책임지도록 분리했습니다.

9. 제 기준의 최종 판별법

언리얼 UI를 깊게 파본 사람인지 확인하는 가장 좋은 질문은 이것입니다.

“버튼이 화면에는 보이는데 클릭이 안 됩니다. 어디부터 보실 건가요?”

깊게 안 본 사람은 이렇게 답합니다.

Is Enabled 확인합니다.
Visibility 확인합니다.

깊게 본 사람은 이렇게 답합니다.

먼저 Widget Reflector로 Hit Test 경로를 봅니다.
상위 위젯 중 HitTest를 막는 오버레이가 있는지 확인합니다.
Visibility가 Visible인지, Self Hit Test Invisible인지 봅니다.
Input Mode와 Focus 대상이 맞는지 봅니다.
Common UI를 쓴다면 현재 활성 Layer와 Input Routing 대상이 맞는지 봅니다.
마지막으로 Slate Tree에서 실제 클릭 가능한 SWidget까지 이벤트가 도달하는지 확인합니다.

이 정도면 “UI를 만들 줄 안다”가 아니라 언리얼 UI 시스템을 이해하고 문제를 구조적으로 해결할 수 있다고 볼 수 있습니다.
