일단 하나 알고가자

<b>인터럽트</b> : 외부에서 발생하는 이벤트에 의해 CPU의 현재 실행 흐름이 변경되는 것을 나타낸다.

### <i><b>인터럽트 벡터 Interrupt Vector</b></i>

- 여러가지 인터럽트에 대해 해당 인터럽트 발생시 처리해야 할 루틴(ISR)의 주소를 보관하고 있는 공간
- 대부분의 CPU들은 인터럽트 벡터 테이블을 가지고 있음

### <i><b>인터럽트 서비스 루틴 Interrupt Service Routine(ISR)</b></i>

- 인터럽트 핸들러 Interrupt handler 라고도 함
- 인터럽트가 접수되면 각각의 인터럽트에 대응하여 특정 기능을 처리하는 기계어 코드 루틴(커널이 실행)
- ex) 키보드 자판을 눌러 키보드 인터럽트가 발생하면 이에 해당하는 인터럽트 서비스 루틴이 실행됨

### <i><b>인터럽트 과정</b></i>

\>> 프로세스 A 실행 중 디스크에서 어떤 데이터를 읽어오라는 명령을 받았을 때

- 프로세스 A는 system call을 통해 인터럽트를 발생시킴
- CPU는 현재 진행중인 기계어 코드를 완료
- 현재까지 수행중이었던 상태를 해당 프로세스의<b> PCB(Process Control Block)</b>에 저장 (수행중이던 메모리 주소, 레지스터 값 등등)
- PC(Program Counter, IP)에 다음 실행할 명령의 주소 저장
- 인터럽트 벡터를 읽고 ISR 주소값을 얻어 ISR(interrupt Service Routine)으로 점프하여 루틴을 실행
- 해당 코드 실행
- 해당 일을 다 처리하면 저장했던 프로세스 상태 복구
- ISR의 끝에 IRET명령어에 의해 인터럽트가 해제
- IRET 명령어가 실행되면, 대피시킨 PC 값을 복원하여 이전 실행위치로 복원
  ![](https://blog.kakaocdn.net/dn/csOicV/btrcebCFFGo/JOr4V3M4umegWKsqdtSV8K/img.jpg)

위의 일련의 과정을 <b>인터럽트</b>라고 한다.

내가 알고있는 시스템 콜은 인터럽트의 한 종류일 뿐ㅇㅇ

커널 모드가 유저 모드를 해결하고 다시 기존 작업(context)를 복구해야한다.

이 과정을 context switching이라고 부른다

### Context Switching

1. <b>인터럽트 처리:</b> CPU는 주기적으로 발생하는 타이머 인터럽트나 외부 이벤트에 응답하기 위해 현재 실행 중인 프로세스를 일시적으로 중단하고, 인터럽트 서비스 루틴(Interrupt Service Routine, ISR)을 실행합니다. 이때 인터럽트 서비스 루틴이 완료되면 이전에 실행 중이던 프로세스로 돌아가야 합니다.
2. <b>스케줄러에 의한 문맥 교환:</b> 운영 체제의 스케줄러가 실행 중인 프로세스를 일시적으로 중단하고 다른 프로세스에게 CPU를 할당하는 경우에도 컨텍스트 스위칭이 필요합니다. 이는 우선순위가 높은 프로세스가 나타날 때, 시간 할당량이 다 찼을 때 등 다양한 이유로 발생할 수 있습니다.

컨텍스트 스위칭은 현재 실행 중인 프로세스의 상태를 보존하고, 새로운 프로세스의 상태를 복원하는 일련의 과정을 포함합니다. 이 과정에는 프로세스의 레지스터 값, 프로그램 카운터, 스택 포인터 등의 상태가 저장되고 복원되는 것이 포함됩니다. 컨텍스트 스위칭이 빈번하게 발생하면 성능에 영향을 미칠 수 있으므로 효율적인 스케줄링 및 인터럽트 처리가 중요합니다.

따라서 현재 context를 저장할필요가 있다.
