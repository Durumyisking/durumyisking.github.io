<b>1. 빌드 요청</b>

에디터에서 Compile을 누르거나, Visual Studio/Rider에서 빌드하거나, 커맨드로 이런 식의 빌드가 호출됩니다.

```txt
Build.bat MyGameEditor Win64 Development -Project=MyGame.uproject
```

여기서 실제 중심은 <code>UnrealBuildTool</code>, 즉 <code>UBT</code>입니다. UBT는 “어떤 cpp를 cl.exe에 넘길지”만 정하는 수준이 아니라, 언리얼식 C++ 프로젝트 전체를 해석하는 빌드 오케스트레이터입니다.

UBT가 읽는 대표 입력은:

```txt
MyGame.uproject
Source/MyGame/MyGame.Build.cs
Source/MyGameEditor.Target.cs
Source/MyGame.Target.cs
*.uplugin
플러그인 Build.cs
엔진 모듈 Build.cs
Config 값 일부
```

<code>Target.cs</code>는 “무엇을 만들 것인가”입니다. 예를 들어 <code>MyGameEditor</code>는 에디터용 게임 모듈을 만들고, <code>MyGame</code>은 독립 실행 게임을 만듭니다.

<code>Build.cs</code>는 “이 모듈은 무엇에 의존하는가”입니다.

```txt
PublicDependencyModuleNames.AddRange(new[] { "Core", "CoreUObject", "Engine" });
PrivateDependencyModuleNames.AddRange(new[] { "Slate", "SlateCore" });
```

이 정보로 UBT는 include path, preprocessor define, 링크할 라이브러리, DLL export/import 규칙 등을 정합니다.

<b>2. UBT가 하는 일</b>

UBT는 대략 이런 걸 결정합니다.

```txt
어떤 Target을 빌드할지
어떤 Module이 필요한지
각 Module의 Public/Private 의존성
어떤 .cpp가 컴파일 대상인지
UHT를 돌려야 하는지
Unity Build를 쓸지
PCH를 만들지
어떤 컴파일러/링커 옵션을 쓸지
증분 빌드에서 무엇만 다시 빌드할지
```

여기서 사용자가 말한 “git 내역도 확인해서 빌드시간 최적화”는 약간 정정이 필요합니다. 보통 UBT가 보는 건 “git history”라기보다는 “현재 작업 중인 파일 목록”에 가깝습니다.

로그에 이런 식으로 뜨는 경우가 있습니다.

```txt
Using 'git status' to determine working set for adaptive non-unity build
```

이건 과거 커밋 기록을 분석한다기보다, 현재 수정/추가된 파일을 보고 “자주 바뀌는 파일은 Unity Build 묶음에서 빼자”는 판단을 하는 쪽입니다.

<b>3. UHT: UnrealHeaderTool</b>

일반 C++에는 런타임 리플렉션이 없습니다. 그런데 언리얼은 이런 걸 지원하죠.

```txt
UCLASS()
class AMyActor : public AActor
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere)
    int32 Health;

    UFUNCTION(BlueprintCallable)
    void Attack();
};
```

<code>UCLASS</code>, <code>UPROPERTY</code>, <code>UFUNCTION</code>, <code>GENERATED_BODY</code>는 단순 장식이 아닙니다. UHT가 헤더를 읽고 UObject 리플렉션용 C++ 코드를 생성합니다.

예를 들어 이런 파일이 있다면:

```txt
Source/MyGame/Public/MyActor.h
Source/MyGame/Private/MyActor.cpp
```

UHT는 대략 이런 생성물을 만듭니다.

```txt
Intermediate/Build/Win64/UnrealEditor/Inc/MyGame/UHT/MyActor.generated.h
Intermediate/Build/Win64/UnrealEditor/Inc/MyGame/UHT/MyGame.gen.cpp
```

<code>MyActor.generated.h</code>는 사용자가 헤더 마지막 쪽에 include하는 파일입니다.

```txt
#include "MyActor.generated.h"
```

<code>MyGame.gen.cpp</code>에는 클래스 등록, 프로퍼티 메타데이터, RPC thunk, <code>StaticClass()</code> 관련 코드 등이 들어갑니다. 그래서 <code>GENERATED_BODY()</code>를 빼먹거나 <code>.generated.h</code> include 순서가 틀리면 일반 C++ 에러가 아니라 UHT/컴파일 에러가 납니다.

<b>4. Unity Build</b>

일반 C++에서는 <code>.cpp</code> 하나가 하나의 translation unit입니다. 예를 들어:

```txt
A.cpp → A.obj
B.cpp → B.obj
C.cpp → C.obj
```

그런데 언리얼 프로젝트는 파일 수가 많고 헤더도 무겁습니다. 매번 각 cpp가 <code>CoreMinimal.h</code>, <code>Engine.h</code> 같은 큰 헤더를 따로 파싱하면 느립니다.

그래서 Unity Build는 여러 <code>.cpp</code>를 하나의 가짜 <code>.cpp</code>로 묶습니다.

```txt
// Module.MyGame.1.cpp 같은 생성 파일
#include "Private/A.cpp"
#include "Private/B.cpp"
#include "Private/C.cpp"
```

그러면 컴파일러 입장에서는 큰 cpp 하나만 컴파일합니다.

장점:

```txt
전체 빌드가 빨라질 수 있음
반복되는 헤더 파싱 감소
컴파일러 프로세스 수 감소
```

단점:

```txt
A.cpp가 B.cpp의 include에 우연히 기대는 버그가 숨을 수 있음
매크로 오염이 다른 cpp에 퍼질 수 있음
작은 파일 하나 수정해도 큰 unity 파일 전체가 다시 컴파일될 수 있음
```

그래서 Adaptive Unity Build가 있습니다. 현재 수정 중인 파일은 Unity 묶음에서 빼고 단독 컴파일합니다.

```txt
자주 안 바뀌는 파일들 → Unity 파일로 묶음
현재 수정 중인 파일 → 단독 .cpp로 컴파일
```

이러면 개발 중 반복 빌드가 더 빨라질 수 있습니다.

<b>5. PCH: Precompiled Header</b>

PCH는 미리 컴파일된 헤더입니다. 언리얼은 공통 헤더가 크기 때문에 PCH 효과가 큽니다.

예를 들어 많은 cpp가 이런 걸 포함합니다.

```txt
#include "CoreMinimal.h"
```

매 cpp마다 이걸 처음부터 파싱하면 비싸니까, UBT는 공유 PCH나 모듈 PCH를 만듭니다.

생성물은 대략 이런 쪽에 생깁니다.

```txt
Intermediate/Build/Win64/x64/UnrealEditor/Development/Core/SharedPCH.Core.Cpp20.h.pch
Intermediate/Build/Win64/x64/UnrealEditor/Development/Engine/SharedPCH.Engine.Cpp20.h.pch
```

이후 cpp 컴파일 시 “이 헤더들은 이미 파싱된 상태에서 시작”하게 됩니다.

<b>6. 전처리</b>

이제 C++ 컴파일러 단계입니다. 전처리는 실제 컴파일 전에 소스 텍스트를 펼치는 과정입니다.

입력:

```txt
MyActor.cpp
MyActor.h
MyActor.generated.h
CoreMinimal.h
각종 include
Build.cs/Target.cs에서 온 define
```

전처리에서 일어나는 일:

```txt
#include 내용 펼치기
#define 매크로 치환
#if WITH_EDITOR 같은 조건부 코드 선택
GENERATED_BODY() 매크로 확장
MYGAME_API 같은 export/import 매크로 확장
```

예를 들어 <code>MYGAME_API</code>는 빌드 상황에 따라 이런 식으로 바뀔 수 있습니다.

```txt
__declspec(dllexport)
__declspec(dllimport)
빈 값
```

Editor용 DLL을 만들 때는 export/import가 중요하고, monolithic Shipping 빌드에서는 비어 있을 수도 있습니다.

전처리 결과물은 엄청 큰 C++ 파일 하나라고 보면 됩니다. 보통 <code>.i</code> 파일로 저장되지는 않지만, 컴파일러 옵션을 주면 볼 수 있습니다.

<b>7. 컴파일</b>

컴파일은 전처리된 C++를 컴파일러가 이해해서 기계어 직전의 object 파일로 바꾸는 과정입니다.

여기서 일어나는 일:

```txt
문법 분석
타입 체크
템플릿 인스턴스화
인라인 판단
최적화
함수/전역변수/가상테이블 코드 생성
디버그 정보 생성
```

결과물은 보통 <code>.obj</code>입니다.

```txt
Intermediate/Build/Win64/x64/UnrealEditor/Development/MyGame/Module.MyGame.1.cpp.obj
Intermediate/Build/Win64/x64/UnrealEditor/Development/MyGame/MyGame.gen.cpp.obj
```

중요한 점은 헤더 파일 자체가 직접 컴파일되는 게 아니라는 겁니다. 헤더는 cpp에 include되어 cpp의 일부처럼 컴파일됩니다. 그래서 공통 헤더 하나를 바꾸면 그 헤더를 include하는 여러 cpp가 다시 컴파일됩니다.

<b>8. 어셈블</b>

전통적인 설명에서는:

```txt
C++ → assembly → object file
```

순서입니다.

현대 MSVC/Clang에서는 이 단계가 내부적으로 처리되어 <code>.asm</code> 파일이 눈에 보이지 않는 경우가 많습니다. 그래도 개념적으로는 컴파일러가 CPU 명령어와 object section을 만들고, assembler가 <code>.obj</code> 형태로 정리한다고 보면 됩니다.

<code>.obj</code>에는 완성된 실행 파일이 아니라 이런 것들이 들어 있습니다.

```txt
기계어 코드
전역 데이터
심볼 이름
아직 해결되지 않은 외부 함수/변수 참조
재배치 정보
디버그 정보 일부
```

예를 들어 <code>MyActor.cpp.obj</code> 안에는 <code>AMyActor::Attack()</code>의 기계어는 있을 수 있지만, <code>AActor::Tick()</code> 같은 외부 심볼은 아직 “나중에 링크 때 찾아줘” 상태일 수 있습니다.

<b>9. 링크</b>

링크는 <code>.obj</code>와 <code>.lib</code>를 모아서 최종 DLL/EXE를 만드는 단계입니다.

Editor 빌드에서는 보통 게임 코드가 에디터에 로드되는 DLL로 만들어집니다.

```txt
Binaries/Win64/UnrealEditor-MyGame.dll
Binaries/Win64/UnrealEditor-MyGame.lib
Binaries/Win64/UnrealEditor-MyGame.pdb
Binaries/Win64/UnrealEditor-MyGame.modules
```

<code>dll</code>은 실제 로드될 코드입니다.

<code>lib</code>는 다른 모듈이 이 DLL을 링크할 때 쓰는 import library입니다.

<code>pdb</code>는 디버깅 심볼입니다. 콜스택, 중단점, 변수 이름 추적에 필요합니다.

<code>.modules</code>나 <code>.target</code> 류 파일은 언리얼이 빌드 산출물을 식별하고 로드하는 데 쓰는 메타데이터입니다.

링크 에러는 보통 이런 종류입니다.

```txt
LNK2019 unresolved external symbol
LNK2005 already defined symbol
```

컴파일은 “이 코드 문법과 타입이 맞는가”를 보는 단계이고, 링크는 “참조한 함수/변수의 실제 구현을 찾을 수 있는가”를 보는 단계입니다.

예를 들어 헤더에는 선언이 있는데:

```txt
void Attack();
```

cpp에 구현이 없으면 컴파일은 통과할 수 있지만 링크에서 터질 수 있습니다.

<b>10. 실행</b>

Editor 빌드 결과를 실행하면 대략 이런 일이 벌어집니다.

```txt
UnrealEditor.exe 실행
OS loader가 필요한 DLL 로드
Unreal Engine Core 초기화
ModuleManager가 엔진/게임/플러그인 모듈 로드
게임 DLL 로드
UHT가 만든 등록 코드 실행
UClass, UFunction, UProperty 메타데이터 등록
에디터가 asset registry, world, blueprint 등을 사용 가능 상태로 만듦
```

그래서 C++에서 만든 <code>UCLASS</code>가 에디터 Content Browser나 Blueprint에서 보이는 건, 컴파일된 DLL 안에 UHT 생성 코드가 들어 있고, 모듈 로드 시 그 클래스 메타데이터가 등록되기 때문입니다.

패키징된 게임은 조금 다릅니다. <code>Package Project</code>는 C++ 빌드만 하는 게 아니라 추가로 이런 단계를 거칩니다.

```txt
Cook: .uasset을 플랫폼용 데이터로 변환
Stage: 실행에 필요한 파일을 staging 폴더에 모음
Pak/IoStore: .pak, .ucas, .utoc 컨테이너 생성
Archive: 배포용 폴더로 정리
```

즉 “빌드”는 주로 코드 산출물 생성이고, “패키징”은 코드 + 에셋 + 설정 + 플랫폼 데이터를 실행 가능한 배포물로 묶는 과정입니다.

<b>11. 증분 빌드</b>

두 번째 빌드부터 빠른 이유는 UBT와 컴파일러가 “안 바뀐 건 다시 안 함”을 하기 때문입니다.

다시 빌드되는 대표 상황:

```txt
.cpp 수정 → 해당 cpp 또는 unity 묶음 재컴파일
.h 수정 → 그 헤더를 include하는 cpp들 재컴파일
UCLASS/UPROPERTY 변경 → UHT 재실행 + generated code 재컴파일
Build.cs 변경 → 모듈 규칙 재평가, 많은 액션 무효화 가능
Target.cs 변경 → 타겟 전체 빌드 설정 무효화 가능
공통 헤더 수정 → 대량 재컴파일 가능
```

빌드 시간이 커지는 흔한 원인은 “많은 cpp가 의존하는 헤더를 자주 바꾸는 것”입니다. 그래서 언리얼 C++에서는 헤더를 가볍게 유지하고, 가능한 cpp로 include를 옮기고, forward declaration을 쓰는 게 빌드 시간에 중요합니다.

<b>12. 한 파일 수정 예시</b>

<code>MyActor.cpp</code> 하나를 수정했다고 해보면:

```txt
1. UBT가 MyActor.cpp 변경 감지
2. Adaptive Unity면 MyActor.cpp를 단독 컴파일 대상으로 둘 수 있음
3. 전처리: include/define/generated.h 확장
4. 컴파일: MyActor.cpp.obj 생성
5. 링크: UnrealEditor-MyGame.dll 다시 생성
6. 에디터가 새 DLL 로드 또는 Live Coding/Hot Reload 처리
```

반대로 <code>MyActor.h</code>에서 <code>UPROPERTY</code>를 바꾸면:

```txt
1. UBT가 reflected header 변경 감지
2. UHT 실행
3. MyActor.generated.h / MyGame.gen.cpp 갱신
4. MyActor.h를 include하는 cpp 재컴파일
5. generated cpp도 재컴파일
6. 링크
```

요약하면, 언리얼 빌드는 “UBT가 언리얼식 모듈 세계를 C++ 컴파일러가 이해할 수 있는 액션 목록으로 바꾸고, UHT가 UObject 리플렉션 코드를 생성한 뒤, 일반 C++의 전처리-컴파일-어셈블-링크 파이프라인을 태우는 과정”입니다. Unity Build, PCH, Adaptive Unity, 증분 빌드는 전부 이 무거운 과정을 조금이라도 덜 반복하려는 장치들이고요.
