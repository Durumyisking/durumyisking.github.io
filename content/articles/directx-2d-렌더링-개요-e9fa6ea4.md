### 라이브러리

- 하나이상의 서브루틴이나 함수의 집합파일
- 분업하기가 수월해짐
- <b>동적 라이브러리 / 정적 라이브러리</b>
  - <b>동적 라이브러리</b>
    - 완성된 프로그램을 실행할 때 포함시키는 라이브러리
      (프로그램 동작중에 포함된다는 뜻)

      윈도우 기준 <b>.dll</b>파일 리눅스는 .so

      동적 라이브러리를 포함하는 프로그램들은

      하나의 동적 라이브러리를 공유하여 사용한다

    - <b>장점</b>
      1. 메모리 절약 가능
      2. 스와핑 현상 적게 일어남
      3. 프로그램을 업데이트/변경시 <b>라이브러리만 빌드해도 된다.</b>
    - <b>단점</b>
      1. 라이브러리 업데이트를 잘못했을때 프로그램이 다운된다.
      2. 런타임중에 변하기때문에 속도가 느리다.

  - <b>정적 라이브러리</b>
    - 프로그램을 컴파일하는 과정에서 포함시키는 라이브러리
      윈도우 기준 <b>.lib</b>파일 리눅스는 .a

      정적 라이브러리를 포함하는 프로그램들은

      각각 정적라이브러리를 가져간다.

    - <b>장점</b>
      1. 라이브러리를 업데이트 할때 원본 프로그램에 영향이 가지 않는다.
      2. 런타임시에 동적라이브러리처럼 다른 메모리에 참조할 필요가 없기 때문에
         속도가 빠르다.

      3. 컴파일시 프로그램에 적재되기 때문에 이식성이 좋다.
    - <b>단점</b>
      1. 동적 라이브러리에 비해서 용량을 많이 차지한다.
      2. 프로그램을 업데이트/변경시 <b>원본 프로그램을 다시 빌드해야한다.</b>
      3. \*<i><b>cpp 파일이 많아져서 Link하는데 시간이 오래 걸린다.\*</b></i>
         1. UnityBuild
            유니티빌드로 극복 가능하지만 오류 생겼을때 제대로 확인할 수 없음

            (유니티빌드 사용 불가능한 곳에서는 오류가 생김)

         <ol type="a" start="2">
         <li>
         인크레디 빌드

         cpp파일 빌드를 코어 개수로 나눠서 개수만큼 한번에 빌드시켜주는 프로그램
         </li>
         </ol>
      4. 해당 정적 라이브러리를 참조하는 프로그램이 많아질수록 메모리 사용량이
         배로 증가한다. 

      5. 재배포해줄때 프로그램을 종료 후 새로 빌드한 후 배포해야한다.

### DirectX 사용 자료형

<b>ID3D11Device </b>: GPU 객체 생성

- Dx10 (멀티 쓰레딩 호환이 강화되기 전)에서는 얘만 사용했었음

<b>ID3D11DeviceContext</b> : GPU read write

- <b>immediately Context</b>
  - 싱글스레드 어플리케이션은 얘만 사용

- <b>differed Context</b>
  - Main 이외의 worker쓰레드들이 사용 가능하는 context

<b>ID3D11Texture2D</b> : 텍스처

- <b>렌더링타겟</b> (API의 dc)으로 사용 가능하다.
- 이는 직접 접근하면 위험하기 때문에 안전한 접근을 위해
  <b>ID3D11RenderTargetView </b>: RenderTargetView를 만든다.

- DepthStencilBuffer으로 사용 가능하다
  이도 안전한 접근을 위해

  <b>IDI3D11DepthStencilView</b> : DepthStencilView 를 만든다.

<b>IDXGISwapChain : </b>렌더링 더블버퍼링 도와주는애

- 더블버퍼링할 backbuffer도 얘가 가지고 있음

<b>ID3D11SamplerState</b> : 텍스처 로딩할때 사용

- 텍스처 계단현상 제거
- 텍스처 불러오는 다양한 모드들이있음
  - <b>AddressMode</b>
    - 텍스처를 어떤 방법으로 그릴건지 선택
