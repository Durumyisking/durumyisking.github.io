근데 이렇게 해버리면 일일히 constructorHelper하기도 불편하고<br />경로라도 바뀌어버린다면..?!? 시간 낭비가 심해진다

<u>하드코딩방법은 항상 지양한다.</u>

언리얼에서는 이를 해결하기위해 <b>AssetManager</b>를 사용한다고 한다.

에셋매니저는 기본적으로 엔진에서 하나의 인스턴스만 지원해서 싱글톤 사용한다.<br />아래 코드를 보면 엔진에 있는 AssetManager를 커스텀으로 캐스팅해서 인스턴스를 가져온다.

```c++
ULCAssetManager& ULCAssetManager::Get()
{
  // GEngine->AssetManager => 엔진단에서 기본적으로 AssetManager를 싱글톤으로 들고있다.
	ULCAssetManager* Singleton = Cast<ULCAssetManager>(GEngine->AssetManager);

	if (Singleton)
	{
		return *Singleton;
	}
	else
	{
		UE_LOG(LogAssetManager, Fatal, TEXT("Cannot use AssetManager if no AssetManagerClassName is defined!"));
		return *NewObject<ULCAssetManager>(); // never calls this
	}
}
```

동기로딩 비동기로딩 사용처

- <b>동기로딩<br /></b>로딩이 완료될때까지 다음 함수를 실행하지 않는다.<b><br />- </b>게임 처음 킬때의 로딩에사용 → 속도가 더 빠르기 때문
- <b>비동기로딩<br /></b>다른 쓰레드에서 로딩을 맡긴다.<br />- 런타임중에 로딩이 필요 할 때 사용

LCManager에서 사용할 이 함수는 동기로딩을 진행할때 느려지거나 한다는 문제가 생겼을때 확인하기 위해서 만든 함수이다.<br />로딩시간이 길면 로그를 확인하자 <br />(확인해서 해당 에셋은 비동기로 뺀다던지의 처리로 당장 필요한 에셋들만 선별해서 로드할 수 있다는 것)

```c++
UObject* ULCAssetManager::SynchronousLoadAsset(const FSoftObjectPath& AssetPath)
{
	if (AssetPath.IsValid())
	{
		// FScopeLogTime을 확인
		TUniquePtr<FScopeLogTime> LogTimePtr;

		// CommandLine에 LogAssetLoads를 넣으면 동기 로딩을 진행할때마다 아래에 로그를 찍게 되는것이다. 
		// 로그찍기싫으면 빼면된다.
		// CommandLine기법
		if (ShouldLogAssetLoads()) 
		{
			// 이 함수가 얼마나 시간을 소모했는지 로깅한다.
			// 이를 통해 AssetPath를 로드하는데 얼마나 시간이 걸렸는지 알 수 있음
			LogTimePtr = MakeUnique<FScopeLogTime>(*FString::Printf(TEXT("synchronous loaded assets [%s]")), *AssetPath.ToString(), nullptr, FScopeLogTime::ScopeLog_Seconds);
		}

		// AssetManager가 있으면 AssetManager의 StreamableManager을 통해 정적 로딩
		// StreamableManager : 동기/비동기 로딩을 관리하는 매니저
		if (UAssetManager::IsValid())
		{
			return UAssetManager::GetStreamableManager().LoadSynchronous(AssetPath);
		}

		// AssetManager가 없으면
		// TryLoad는 매우 느리기때문에 사용을 지양한다.
		return AssetPath.TryLoad();
	}

	return nullptr;
}

```

위에 적었듯이 TryLoad는 LoadSynchronous보다 매우 느리다고 한다.<br />(주석에 VerySlow라고 적혀있음)

이제 아래 함수를 사용해 <b>GetAsset이라는 함수를 통해 Bpclass,Object를 CDO처럼 불러오게 될 것이다</b>.

```c++
template<typename AssetType>
inline AssetType* ULCAssetManager::GetAsset(const TSoftObjectPtr<AssetType>& AssetPointer, bool bKeepInMemory)
{
	AssetType* LoadedAsset = nullptr;
	const FSoftObjectPath& AssetPath = AssetPointer.ToSoftObjectPath();

	if (AssetPath.IsValid())
	{
		LoadedAsset = AssetPointer.Get();
		if (!LoadedAsset)
		{
			LoadedAsset = Cast<AssetType>(SynchronousLoadAsset(AssetPath));
			ensureAlwaysMsgf(LoadedAsset, TEXT("Failed to load asset [%s]"), *AssetPointer.ToString());
		}

		if (LoadedAsset && bKeepInMemory)
		{
			// 에셋을 메모리에 캐싱하기 위한 장치
			// 강제로 unload하는한 GC에 의해 unload되지 않는다.
			Get().AddLoadedAsset(Cast<UObject>)LoadedAsset));
		}
	}

	return LoadedAsset;
}
```

- <b>FScopeLock Lock(&SyncObject)<br /></b>이걸 왜 걸까요?<br />⇒ 여러쓰레드가 비동기적으로 에셋을 로드하는데 한놈만 들어오라고 막아둔것<br />(그냥 임계영역 설정한거임)<br />CDO를 만들거나 AssetManager에서 로드하거나 할 때 UObject시스템의 스레드 안전성이 보장되지 않을수도 있다.<br />아니 그냥 UObject시스템 말고도 스레드 안전한지가 보장이 안된다
  <aside class="callout">

  <b>강사님 답변</b>

  어떠한 에셋을 로드하는 과정 자체를 언리얼에서는 게임 스레드 말고 다른 스레드로 Task 형태로 던져서 시킬 수가 있어요.<br />만약에 100개를 로드해야 한다고 가정하면 20개씩 다른 스레드로 Task 형태로 던지면 정말 속도가 빠르거든요.

현재 <code>UOWAssetManager</code>는 두 가지 역할이 핵심이다.

1. 엔진 시작 초기 구간에서 Native GameplayTag 등록
2. SoftObject/PrimaryAsset을 로드하고 필요하면 메모리에 붙잡아두기

```c++
void UOWAssetManager::StartInitialLoading()
{
    Super::StartInitialLoading();
    FOWGameplayTags::InitializeNativeTags();
}
```

이 호출 때문에 <code>InitState.Spawned</code>, <code>InputTag.Move</code> 같은 Native Tag가 에디터/게임 시작 전에 등록된다.

즉 InitState나 InputConfig가 GameplayTag를 쓰기 전에 AssetManager가 먼저 기본 태그를 올려주는 구조다.

```c++
UObject* UOWAssetManager::SynchronousLoadAsset(const FSoftObjectPath& InAssetPath)
{
    if (!InAssetPath.IsValid())
    {
        return nullptr;
    }

    if (IsInitialized())
    {
        return GetStreamableManager().LoadSynchronous(InAssetPath);
    }

    return InAssetPath.TryLoad();
}
```

<code>GetAsset</code>, <code>GetSubclass</code>는 <code>TSoftObjectPtr</code> 또는 <code>FPrimaryAssetId</code>를 받아 실제 UObject/Class로 바꿔준다.

그리고 <code>bKeepInMemory</code>가 true면 <code>LoadedAssets</code>에 저장해서 GC로 날아가지 않게 잡아둔다.

```c++
void UOWAssetManager::AddLoadedAsset(UObject* InAsset)
{
    if (!InAsset)
    {
        return;
    }

    FScopeLock Lock(&SyncObject);
    LoadedAssets.Add(InAsset);
}
```

여기서 <code>FScopeLock</code>을 거는 이유는 LoadedAssets가 여러 로딩 흐름에서 동시에 건드려질 수 있기 때문이다.

AssetManager는 단순 로더가 아니라, 프로젝트의 "에셋 참조 안정성"을 책임지는 쪽으로 보면 된다.
